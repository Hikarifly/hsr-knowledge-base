# ADR-0002 · 权威层级与术语唯一

> **Status**：Accepted（2026-11-15 聚合定稿；D-066 为最近一次修订）
> **覆盖决策**：D-002、D-066、D-071
> **相关**：`GLOSSARY.md`、`协作要求与行动准则.md` §十/§十一

## Context

文档体系盘点（`docs/pipeline/docs-inventory.md`）暴露出三个同源问题：

1. **同一规范多版本并存**：同一份 `格式规范与要求.md` 在不同文档里被标成 v1.13 / v1.14 / v1.16；
2. **术语分裂**：静态站视觉约束先后被写成「三禁」（旧工单 W-4.6-94/95）与「四禁（含毛玻璃）」（W-4.6-67），而校验器实际只跑 6 条正则；
3. **猜测性称呼**：MCP 项目名被写成 `obsidian-kb-mcp` 等，命中几乎全在本地备份副本里。

根因是「叙述性文字」与「已生效决策」没有裁决顺序，谁写得多谁看起来更权威。

## Decision

1. **四级权威层级**（高位直接覆盖低位，低位须就地修正或标注作废）：
   | 级别 | 层级 | 典型载体 |
   |---|---|---|
   | 1 | **实测**（真实命令输出、文件内容、`git diff`） | `gen_metrics.py`、`build_wiki.py`、`verify_*`、`git ls-tree` |
   | 2 | **决策记录 `D-*`** | `docs/prompts/决策记录.md` |
   | 3 | **规范** | `格式规范与要求.md`、`翻译办法.md`、`协作要求与行动准则.md`、`docs/仓库结构.md` |
   | 4 | **叙述** | `README.md`、`docs/README_*.md`、`update.md`、工单与评审 |
   执行方不得自行推翻 `D-*`；有异议走「带证据的异议 → Lead 裁定」（D-002）。
2. **术语唯一**：视觉约束一律写「**六禁**」，判定面以 `tools/verify_site.py` 的 `check_banned()` 实际 6 条正则为准；毛玻璃 / 玻璃拟态**不在**判定面内，不得口头宣称已禁；SVG 驼峰写法（`linearGradient`）属合法逃逸，靠代码审查封住（D-066）。
3. **专名以实物为准**：MCP 项目名以实际仓库名 `markdown-kb-mcp` 统一，删除文档正文里的猜测性叫法（D-071）。
4. **配套纪律**：规范与上位冲突时就地修订并升版本号 + 写改动摘要；任何规模数字必须自带「入库 / 工作区 / 详情」口径。

## Consequences

- **正面**：争论可机械裁定；术语与判据一一对应，评审不再靠记忆；文档版本号收敛。
- **负面**：每次裁定都要回写规范与术语表，短期增加文档工作量。
- **风险**：层级 1「实测」依赖命令可复跑——若命令本身 cwd 错位（见 ADR-0011），会把假证据当权威，因此验收命令必须写死运行目录。

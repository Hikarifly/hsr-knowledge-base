# ADR-0016 · 提交发布与 issue 治理

> **Status**：Accepted（2026-11-15 聚合定稿）
> **覆盖决策**：D-036、D-063、D-064、D-077、D-079
> **另见**：主线 E 闸门细则 = D-078（挂 `ADR-0011` 口径与 `docs/ROADMAP.md` 主线 E）
> **相关**：`ADR-0002`、`协作要求与行动准则.md` §七

## Context

仓库为 public，push 即触发 GitHub Pages 构建；同时接受外部投稿（PR #1 来自社区作者）。
治理上出现过两个偏差：一是「工作区改了就等于线上改了」（撤下类操作未进版本库，见 ADR-0006）；二是「先改后补 issue」，导致修复无对外可追踪的入口。

## Decision

1. **提交与推送等用户明确指令**：工作区改动可以先积累，未获指令不提交、不 push（D-036）。此条不适用于「已获放行的收口」——放行后应尽快落地，避免长期悬挂。
2. **push 前必跑两件**：`verify_links.py`（数据区死链 0）与 `wiki/build_wiki.py`（构建通过）；触及文档数字时加跑 `gen_metrics.py` + `verify_site.py`（D-024 的纪律被沿用）。
3. **外部 PR 一律「并入后自行修正」**：`gh pr merge --squash`，作者署名写入提交信息，随后按库内规范就地修正，不要求作者回改再提（D-063）。
   - 注意：`--squash` 会在 fork 线上留孤儿提交；后续外部 PR 建议改用 `--merge`。
4. **发现缺陷先立 issue 再改**：任何缺陷 / 待补项先用 `gh issue create` 建单（标题前缀分类如 `[世界观]` / `[镜像]` / `[数据]`，正文含「现象 / 期望 / 已知依据 / 验收」），修复提交引用 `refs #N` / `closes #N`；不得先改后补，也不得只写进 `docs/待补充清单.md` 了事——台账是内部记录，issue 是对外入口，两者并存（D-064）。
5. **收口即更新交接单**：跨会话的长任务维护一张交接 issue（现状 / 未提交清单 / 未验证项 / 阻塞项 / 环境坑），完成一项回填一项。
6. **一切任务先立 issue**（D-077，2026-11-15 扩展 D-064）：任何执行性任务——改数据、改代码、改文档结构、批量口径调整、新建产物——**开工前必须已有 issue**；issue 可先简后详，但**不得先做后补**。例外只有两类：①纯只读查询与取证；②用户明确指派「继续 / 收口」且该 issue 已存在。收口时必须在 issue 回填证据（命令输出、提交号、未做项）。
7. **接收 issue 后先生成工单**（D-079）：在该 issue 下追加一条「工单」评论（现象 / 根因 / 方案 / 验收），状态流转（已接收 → 工单已生成 → 修复中 → 已修复待验收 → 关闭）写在评论头部并**编辑同一评论**跟踪，不刷屏。

## Consequences

- **正面**：线上与版本库一致；每条修复都有可点开的入口；外部贡献者不被流程卡住。
- **负面**：先立 issue 会拉长单个修复的链路；push 前的验收串行耗时。
- **风险**：`--squash` 的孤儿提交会让 network 图出现不回汇的分支，读者可能误判进度——需在 issue 或 `update.md` 说明。

# ADR-0014 · 数据源与取证通道

> **Status**：Accepted（2026-11-15 聚合定稿；D-058 为最近一次修订）
> **覆盖决策**：D-013、D-035、D-057、D-058
> **相关**：`数据来源.md`、`SRR图包来源.md`

## Context

本库有四个数据源（nanoka 静态站、米游社官方 Wiki、HoYoverse 官网、StarRailRes），取证方式各不相同；同一事实在不同源上可能给出不同数字（源 JSON 实体数 vs 库内文件数）。
2026-11-14 的 4.7 入库把「怎么取证」变成瓶颈：逐页渲染既慢又易触发风控，而官方侧其实有批量 API。

## Decision

1. **引用可稳定寻址**：引用外部 wiki 一律用 pageid 稳定 URL（`?curid=<id>`），不用含未编码全角字符的页面名 URL（D-013）。
2. **批量 API 优先于逐页渲染**：取证首选官方批量接口，落地为可复跑脚本 + 清单（D-057）。4.7 落地两个脚本：Hoyoverse 内容 API（`getContentList` / `getContent`）与米游社 bbs API。
3. **通道选型以用户口径为准**：D-058 明确首选 DeepSeek 官方「网页搜索与抓取」API（`/v1/tools/search`、`/v1/tools/fetch`），并承认 D-057 先用游戏侧 API 属偏差。今后取证通道按此优先级：官方批量 API → DeepSeek 搜索/抓取 → 浏览器渲染。
4. **两份 SRR 克隆长期保留**（约 3.1 GB，`.gitignore` 不入库）：`StarRailRes-master/`（13 语言 JSON，ZIP 快照）与 `StarRailRes_repo/`（git 克隆，可 pull）（D-035）；用途分工写进 `SRR图包来源.md`。
5. **源计数 ≠ 库内规模**：源 JSON 的实体条数（如祝福 1219）与库内文件数（906，同名合并后）是两种口径，**不得互相校验**；对外只看库内文件数。

## Consequences

- **正面**：取证可复跑、可限速、可留清单；4.7 的公告与活动名称都有可追溯的 API 来源。
- **负面**：依赖第三方 API 的可用性与配额，脚本需处理缓存与去重。
- **风险**：源站条款各异（官方 Wiki 禁止转载），取回的文本只能作事实提取，不能整段搬运（见 ADR-0006）。

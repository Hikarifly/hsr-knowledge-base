# ADR-0015 · 站点生成与图片策略

> **Status**：Accepted（2026-11-15 聚合定稿；首页形态由 D-053 定稿）
> **覆盖决策**：D-014、D-015、D-053
> **相关**：`wiki/build_wiki.py`、`tools/verify_site.py`、`ADR-0012`

## Context

`wiki/` 是纯静态站点（GitHub Pages），生成物不入库。两个长期约束决定了它的实现方式：

1. **不分发游戏美术**：仓库不能包含图标与立绘，但站点又需要图标才可用；
2. **视觉硬约束**：六禁（无圆角 / 无阴影 / 无渐变 / 无非图标图片 / 无外链脚本 / 无外链样式）必须由校验器机械判定。

首页则经历了一次重做：从「数据罗列」改为「搜索 + 类目」优先，并要求两版信息架构对照后再定稿。

## Decision

1. **图片走 CI 拉取**（D-014 方案 B）：浅克隆 StarRailRes → 只复制用到的图标进构建产物；**图片一律不入库**；范围 = 小图标 + 角色立绘大图。用户在知情素材版权风险的前提下接受了公开展示。
2. **图片注入只改生成器**：不改任何 `.md`；无图标一律占位降级，**构建不得因缺图失败**（D-015）。
3. **首页信息架构**（D-053）：首屏 = 搜索框 + 13 类目入口；区块只保留 6 个（规模仪表 / 版本分布 / 类目导航 / 最新收录 / 图标库存 / 角色速览）；两版原型（搜索优先 `a-search.html` / 看板优先 `b-dashboard.html`）同数据同约束对照后再定稿。
4. **判据复用而非重写**：验收直接复用 `verify_site.py::check_banned`，不另写一套视觉判据；验收加码项含「纯净检出可渲染」（等价 CI 环境）。
5. **站点验收是提交前提**：任何触及 `wiki/` 的改动，提交前必须 `verify_site` `[1]–[16]` 全 PASS。

## Consequences

- **正面**：仓库体积可控、移动端可用、素材合规边界清晰；视觉约束不可被「看起来没问题」绕过。
- **负面**：本地预览必须先跑构建并联网取图标；CI 构建比纯静态站慢。
- **风险**：图标来自第三方仓库，上游改名会致缺图——降级路径已固定（占位符），不会阻断发布。
